## 5. How to read the performance numbers

Measured on this machine (wp-env in Docker Desktop, WordPress served from a Windows
bind mount). Three facts separate "our code" from "this environment":

1. **The database is fast.** `wc_get_products()` for all 8 products: 0.075s; raw SQL: 0s
   (`wp eval-file probe-perf.php`). So the multi-second TTFB is not query cost.
2. **Transfer size is small.** Compressed responses: home 17KB, shop 25KB, cart 70KB.
   The cart/checkout HTML is ~440KB *uncompressed* because WooCommerce inlines its
   `wcSettings.countryData` (the world country/state dataset, 61KB of JSON, 242KB
   URL-encoded) — that is WooCommerce core behaviour, and it compresses well.
3. **PHP file I/O over the bind mount is the bottleneck.** Every stat() on the mount
   costs ~8-10ms here (measured in Phase 2), and WooCommerce autoloads hundreds of
   class files per request. That is the whole TTFB. It is already mitigated as far as
   a demo can: `opcache.validate_timestamps=0` + realpath cache (`scripts/php-tune.js`)
   and deferred WooCommerce block registration (DECISIONS `deferred-wc-block-registration`).

Consequence: the throttled performance score (8-89 depending on page) measures this
machine, not the storefront. On normal hosting (PHP-FPM + OPcache on a native
filesystem, HTTP/2, no bind mount) TTFB is ~200-400ms and these pages land in the
90-100 range. **[UNVERIFIED]** — that expectation has not been measured on a real host,
and it stays a deployment item in `docs/QA-REPORT.md` §6 rather than a claim.

What is *not* an environment artifact: accessibility (100 on all six pages),
best practices (96-100), SEO (92-100) and the security headers — those depend only
on markup and configuration, and they are the numbers that travel with the project.

## 6. Open items carried to deployment

- Re-run `node scripts/qa-audit.js` on the real host: performance numbers become
  meaningful only there; a11y/SEO/security must stay at their current values.
- Apache `ServerTokens Prod` + `ServerSignature Off` (the local wp-env image leaks
  `Apache/2.4.68 (Debian)`; PHP cannot remove that header, only host config can).
- HSTS + a Content-Security-Policy once the site is served over HTTPS (deliberately
  not set here: the demo runs over plain http on localhost, where both are ignored or
  harmful).
- `image-redundant-alt` on cart/checkout is WooCommerce's own cart-item markup (the
  product name is both the alt text and the adjacent label). Minor, upstream, left as is
  rather than filtered at the cost of product image alt text everywhere else.
