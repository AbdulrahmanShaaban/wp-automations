# Security Audit — Siraj Dental Clinic Demo (P3, `p3-clinic`)

**Date:** 2026-10-07 · **Mode:** READ-ONLY (no PHP/HTML/CSS/JS, theme, plugin, `scripts/`, `.wp-env.json`, `package.json`, `design/` or `README.md` change; `scripts/verify.sh` and `scripts/seed.sh` NOT run; the only files written are this report and `docs/AUDIT/evidence/security/**`)
**Target:** http://localhost:8889 — WordPress **7.1.3** + block theme `siraj-theme` 0.1.0 + plugin `siraj-core` 0.1.0, **no WooCommerce**; local wp-env (Docker), Apache/2.4.68 (Debian) + mod_php, PHP 8.3.35, MariaDB
**Scope:** the 9 checks in the audit brief — HTTP security headers, secrets handling, upload/media handling, exposure & enumeration, booking-form/endpoint validation, CPT privacy & PII, attack-surface inventory, authentication surface, handoff-as-demo review
**Evidence root:** `docs/AUDIT/evidence/security/` (176 files — 155 captures + 21 re-runnable scripts under `tools/`, indexed at the bottom)

> **Severity context:** this is an **explicit local demo** that will be handed to a client as **source**, not deployed to the internet. Severities are therefore rated against two questions: (a) is the demo insecure *right now* on localhost:8889? and (b) does the artifact hand a client an exploitable default? Items that only matter behind a real TLS terminator, a WAF, or a public IP (HSTS, DDoS, distributed brute force, `wp-cron`→system cron) are called **deployment items** and are listed separately in their own section — they are not counted as code defects. No claim below is asserted without a captured status code, header, or file:line behind it.

**Tooling notes for whoever re-runs this:** `npx @wordpress/env` (the form in the brief) **fails** on this machine — it fetches `@wordpress/env@11.17.0` fresh and answers `Environment not initialized`; the project-local `npx wp-env` (11.16.x from `node_modules`) works. Quoting a long `bash -c` payload through PowerShell → `npx` mangles inner double quotes, so every container script was piped over stdin instead (`type file | docker exec -i <container> bash -s`); the container is **BusyBox**, so `grep --include` does not exist and `php.ini-production|development` are templates, not the loaded ini. Plain PowerShell has no `grep`/`find`, and nested quotes passed through PowerShell into `bash -c` get mangled — the one grep-style evidence file (`check2-header-code-grep.txt`) was therefore produced by the re-runnable script `tools/check2-header-code-grep.sh`, executed via Git bash (`& "C:\Program Files\Git\bin\bash.exe" <script>`).

## 5 highest-impact fixes

1. **Kill the publicly-known salts before this source leaves the machine** — all 8 `AUTH_KEY`/`*_SALT` constants currently equal the hardcoded wp-env fallback (finding #1); make `wp config shuffle-salts` the mandatory first step in the handoff README, together with `WP_DEBUG=false`.
2. **Send the front-end security headers from `siraj-core`** — all five pages plus the 404 carry **0 of 7** security headers while core's own `wp-login.php` already carries three (finding #2); it is ~12 lines on `send_headers` and it is the single biggest gap between this build and the P1 build.
3. **Stop displaying PHP errors** — `WP_DEBUG=true` with `WP_DEBUG_DISPLAY` defaulting to true forces `ini_set('display_errors', 1)` (finding #3); set `"WP_DEBUG_DISPLAY": false` in `.wp-env.json` so a single notice cannot leak paths and SQL.
4. **Close enumeration + brute force + XML-RPC** — three one-liners with three endpoints retired: kill `/?author=1` (leaks the sole `admin` login), rate-limit or block `wp-login.php`, and deny `xmlrpc.php` (79 live methods including `system.multicall`) (findings #4-#6).
5. **Throttle the booking form** — nonce + honeypot are the only gates and the plugin already computes a keyed IP hash it never uses for rate control (finding #7); a per-hash transient turns an unbounded INSERT+meta-write flood into a bounded one.

## Deployment items (explicitly *not* code defects)

These are real requirements for a public clinic site but they belong to the server/CDN layer, not to this repository, and they are **not** counted in the severity tally above:

- **TLS + HSTS.** The target is plain-HTTP `localhost:8889`; HSTS is meaningless without a TLS terminator, and `Strict-Transport-Security` was absent on **17 of 17** endpoints for that reason.
- **WAF / DDoS / distributed brute force.** Exactly **one** failed login attempt was made; no rate, no volume, no sustained testing was performed. Finding #6 is about the *absence of any limiter*, measured from the installed-plugin list and from one un-throttled 200.
- **System cron instead of web cron.** Finding #15 records that `wp-cron.php` is reachable; the fix on a server is `DISABLE_WP_CRON` + a real crontab, not application code.
- **Full CSP tuning.** Finding #2 asks for `frame-ancestors`/`object-src`; a production CSP needs the site's real asset origins measured first, which is out of scope for a read-only header audit.
- **Apache hardening as a deliverable.** `ServerTokens Prod`, `ServerSignature Off`, and `RedirectMatch 404 ^/\.git` are currently commented-out stock lines (`security.conf:12,23,51`) — real, but they belong in whatever `.htaccess`/vhost the client deploys.
- **Update-check traffic.** 9 scheduled hooks phone WordPress.org from the container (`check5-6-db-and-cpt.txt` §G); egress policy is an ops decision.
